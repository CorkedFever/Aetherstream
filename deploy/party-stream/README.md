# Party stream — one source, many watchers

Lets the group watch something together when only *you* have access to it. You push one stream to
the droplet; everyone plays a URL. Nobody else needs a Plex account, and nobody sees your library.

The plugin needs no changes: an HLS URL goes through the direct-media path, the same one a Twitch
stream takes.

```
your PC ──ffmpeg/SRT──> luna (MediaMTX) ──HLS──> everyone's plugin
   one upload               fan-out            /aether play <url>
```

## Why this shape

- **One upload from you.** Six viewers do not mean six uploads off your connection.
- **Sync comes free.** It becomes a live broadcast, so everyone sits a few seconds apart the same
  way Twitch viewers do. No position messages, no seek corrections, no per-viewer offsets.
- **You control playback**, because you are the thing feeding the stream.
- **Near-zero CPU** if the file is already H.264/AAC — ffmpeg copies the streams rather than
  re-encoding them.

Be clear-eyed about what it is: this is redistribution, not Plex's per-account sharing. Anyone with
the link can watch, there is no per-person revocation, and the bytes are yours. Fine for a handful
of friends on an unlisted URL; do not publish the link anywhere.

## As deployed on luna

| Thing | Where |
| --- | --- |
| Compose project | `/opt/tsukino/party-stream` — its own project, not part of the moonlighting stack |
| Network | joins `moonlighting_default` so Caddy can reach it as `party-stream:8888` |
| Ingest | SRT, UDP **8890**, passphrase-encrypted. RTMP is off. |
| Delivery | HLS on 8888, **not published** — Caddy is the only way in |
| Secrets | `party.env` and `mediamtx.yml` on the server, both `chmod 600`, generated by `setup.sh` |
| Caddy site | `party.example.com:8443` in `moonlighting/deploy/stage/Caddyfile` |

It is a separate compose project on purpose: it can be stopped, moved to its own droplet, or thrown
away without touching anything that serves the websites. Joining their network is the same
arrangement the production app container already uses.

## The two things that will waste your afternoon

### libvlc cannot fetch HLS through Caddy over HTTP/2

This is why the stream is on port 8443 rather than 443. Through Caddy's default HTTP/2, libvlc 3
aborts every segment and decodes nothing:

```
[Error] http: local stream 1 error: Cancellation (0x8)     <- HTTP/2 RST_STREAM CANCEL
[Error] access: HTTP connection failure
```

The identical stream over HTTP/1.1 plays immediately. Proven by bypassing Caddy entirely with an
SSH tunnel straight to the container: 13 video and 87 audio callbacks, versus zero through Caddy.

Caddy sets protocols **per listener, not per site**, so isolating it needs its own port:

```caddy
{
	servers :8443 {
		protocols h1
	}
}

party.example.com:8443 {
	reverse_proxy party-stream:8888
}
```

The websites keep HTTP/2 on 443. Verified after the change: all sites `http/2`, party `http/1.1`.

### A long keyframe interval looks exactly like a broken stream

HLS can only cut a segment on a keyframe. libx264 defaults to roughly an 8-second GOP, while
`hlsSegmentDuration` is 2s — so the muxer cannot close a segment on time, and libvlc reports
`state: Playing` with the streams correctly identified and then delivers **zero frames**. It looks
like a decode failure; it is an encoding mismatch.

Measured on the same 120-second clip, pushed with `-c copy` both times:

| Source GOP | Result |
| --- | --- |
| libx264 default (~8s) | Playing, 0 video / 0 audio callbacks |
| `-g 60` (2s at 30fps) | Playing, 11 video / 86 audio callbacks |

`push.ps1` checks the first 12 seconds of any file it is about to copy and re-encodes instead if the
keyframes are more than 4 seconds apart. Pre-encoding party copies with `-g 60` avoids that
re-encode entirely.

### The Caddyfile is a single-file bind mount, so editing it is a silent no-op

`deploy/stage/Caddyfile` is mounted as one file, which pins it to that inode at container start.
Edit it on the host and the container keeps serving the old content — and `caddy validate` and
`caddy reload` both **succeed**, because they read the container's stale copy. The host file had 76
lines while the container saw 62.

Only a container restart picks it up. Mounting the *directory* instead would fix this properly.

## Setup, once

```bash
cd /opt/tsukino/party-stream
./setup.sh              # generates the secrets; refuses to overwrite an existing config
docker compose up -d
```

`setup.sh` writes `mediamtx.yml` and `party.env` (both `chmod 600`) and prints the watch URL. The
path name is the read secret — it is what protects the stream, so it is long and random.

## Codes, not configuration

Nobody is going to SSH into a droplet and copy five secrets into a form. There are two codes, and
each is one thing to copy and one thing to paste.

```bash
cd /opt/tsukino/party-stream && ./code.sh party.example.com:8443
```

- **Host code** (`AETHER-H-…`) — paste once into the plugin's Share tab and it is configured:
  address, path, publish password, SRT passphrase. **Private.** It carries the credentials that let
  someone broadcast as you.
- **Invite code** (`AETHER-J-…`) — what you send the room. They paste it into the ordinary Source
  box and press Play. Nothing to set up first, no server address to type.

### Starting a new party is the revocation

There is no per-person revocation and there never will be — anyone holding an invite can watch. What
there is instead: **New party** in the Share tab mints a fresh path, and every invite handed out
before that is left pointing at a stream nobody is publishing to. `./code.sh <watch-host>` does the
same from the server; add `--keep` to reuse the existing path.

This works because the relay matches paths by pattern rather than by name:

```yaml
paths:
  "~^party-[0-9a-f]{24}$":
    source: publisher
```

So a new party needs no server edit, no restart, and no SSH. Measured against the live relay:

| Path | Result |
| --- | --- |
| freshly minted, never configured | HTTP 200, plays |
| a path with nobody publishing | HTTP 404 |
| anything not matching the pattern | HTTP 500 |

It is not a hole. Publishing still needs the password, and the path is 96 bits from a cryptographic
source — a reader guessing one finds nothing unless somebody is pushing to that exact path.

The prefixes differ so the private one is hard to send by accident, and pasting the wrong one says
so rather than failing silently. Codes survive how they actually arrive: backticks, bold, quotes,
mid-sentence, a trailing full stop, or a newline through the middle. They are **case-sensitive**,
being base64 — an uppercased code cannot be recovered.

An invite code carries the stream, and optionally the host's screen (below). It never carries the
publish credentials — verified by decoding the payload and checking.

### The screen travels; the placement does not

A guest who has never done the surface scan would otherwise get a stream with nowhere to put it. So
the invite can carry **which furnishing and texture** the host is painting on, plus mask, brightness
and fit. The guest gets a one-click "Use that screen" the first time they play the code.

What is deliberately left out is **world placement** — position, facing, territory, anchor object.
Those are coordinates in the host's house; in a guest's they name a spot inside a wall. Sharing them
would half-work whenever two people happen to share a layout, and silent half-working is worse than
never working.

This only helps a guest who owns the same furnishing. Standing next to their own copy is the
requirement, because the surface is resolved by model path near where they are.

## Movie night

The **Share tab** in the plugin does all of this without leaving the game: it probes the source,
picks copy or re-encode, starts ffmpeg as a child process and shows the throughput, and hands you
the `/aether play` line on the clipboard. Fill it in once by pasting `party.env` into it.

`push.ps1` does the same from a terminal, and `BroadcastSession` is shared by both, so the two
cannot drift apart.

**Push by hand**, with a file or a Plex direct-play URL as the input. Credentials come from
`party.env`:

```bash
ffmpeg -re -i "INPUT" -c copy -f mpegts \
  "srt://your.server.example:8890?streamid=publish:${PARTY_PATH}:publisher:${PARTY_PUBLISH_PASS}&passphrase=${PARTY_SRT_PASSPHRASE}&pkt_size=1316"
```

- `-re` paces the file at real time. Without it ffmpeg blasts the whole film upstream as fast as it
  can and viewers get nothing sensible.
- `-c copy` avoids re-encoding. It only works if the file is already H.264 + AAC — which is exactly
  what the pre-encoded party copies are for. If it is not, swap in
  `-c:v libx264 -preset veryfast -b:v 3M -c:a aac -b:a 160k`, and expect real CPU load.

**Watch** — everyone runs:

```
/aether play https://party.example.com:8443/<path>/index.m3u8
```

Their placement, sizing and volume stay their own; only the picture is shared.

## Nothing is stored on the droplet

- **The film is never copied to the droplet.** MediaMTX holds a rolling window of about 14 seconds
  in memory and discards segments as they age out. Stop the push and there is nothing left.
- `record: no` lives under `pathDefaults` — a bare top-level `record` is accepted but deprecated,
  and a silently-ignored key is not what you want holding up that promise.
- `hlsDirectory` is unset, so nothing is written to disk even by accident.

## Things worth knowing

- **Bandwidth.** Roughly `bitrate × viewers × runtime` of droplet egress. At 3 Mbps, six people, two
  hours, that is about 16 GB per film. Check the monthly transfer allowance before making a habit.
- **Seeking.** Nobody can scrub, including you — it is a live stream. To skip, stop ffmpeg and
  restart it with `-ss <timestamp>`. Everyone follows within a few seconds.
- **Stopping ffmpeg ends it for everyone.** That is the point, but it also means a dropped
  connection on your end ends movie night; the plugin will show the stall message.
- **Encode the party copies once**, at 720p / ~3 Mbps / H.264 High + AAC, MP4 with
  `-movflags +faststart` **and `-g 60 -keyint_min 60 -sc_threshold 0`** (see the keyframe note
  above — without it the copy path cannot be used). The plugin decodes at 1280×720 onto a small in-game surface, so anything
  higher is invisible and just costs upstream.
- **MoQ is off.** MediaMTX 1.20 starts Media-over-QUIC listeners by default and generates a
  certificate for them on first run; none of that is wanted here.
